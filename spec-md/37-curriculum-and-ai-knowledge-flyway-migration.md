# 38 — Step 12A: Curriculum and AI Knowledge Base Flyway Migration

**Project:** Smart AI University Student Assistant
**Module:** Academic Management / Curriculum Management / AI Knowledge Base
**Scope:** PostgreSQL Flyway migration only
**Database:** `smart_university_db`
**Stack:** Java 21, Spring Boot 4.x, PostgreSQL, Maven, Flyway

## 1. Objective

Create a clean, normalized PostgreSQL schema for managing official university curriculum versions and knowledge documents.

This schema must support:

- Curriculum versions belonging to academic programs
- University-wide and program-specific documents
- Document categories/types
- Academic-year labels
- Uploaded file metadata
- File replacement/revision history
- Document processing state
- Active/archive lifecycle
- Admin audit information
- Future RAG processing

Do not implement controllers, services, repositories, uploads, or Gemini retrieval in this migration task.

## 3. Final Database Design

Create five tables:

```text
curriculum_versions
document_categories
academic_documents
academic_document_files
academic_document_processing
```

Relationships:

```text
programs
   |
   | 1:N
   v
curriculum_versions
   |
   | 1:N (optional)
   v
academic_documents <---- document_categories
   |
   | 1:N
   v
academic_document_files
   |
   | 1:1
   v
academic_document_processing
```

An academic document may be university-wide, department-scoped, program-scoped, or linked to a curriculum version.

Do not force every document to belong to a program. University regulations and campus safety documents may apply to all students.

## 4. Table 1 — curriculum_versions

Purpose: represent official curriculum revisions for a program.

| Column                | PostgreSQL type | Constraint                  |
| --------------------- | --------------- | --------------------------- |
| `id`                  | BIGINT          | Identity PK                 |
| `program_id`          | BIGINT          | NOT NULL, FK `programs.id`  |
| `version_code`        | VARCHAR(50)     | NOT NULL                    |
| `version_name`        | VARCHAR(200)    | NOT NULL                    |
| `academic_year_label` | VARCHAR(20)     | NOT NULL                    |
| `description`         | TEXT            | NULL                        |
| `effective_from`      | DATE            | NULL                        |
| `effective_to`        | DATE            | NULL                        |
| `status`              | VARCHAR(20)     | ACTIVE / ARCHIVED           |
| `is_deleted`          | BOOLEAN         | NOT NULL DEFAULT FALSE      |
| `created_by`          | BIGINT          | FK `app_users.id`, nullable |
| `created_at`          | TIMESTAMP       | NOT NULL                    |
| `updated_by`          | BIGINT          | FK `app_users.id`, nullable |
| `updated_at`          | TIMESTAMP       | NULL                        |

Rules:

- A curriculum version always belongs to an existing Program.
- Program and Department are not duplicated within `curriculum_versions`.
- `version_code` is unique within a Program.
- Only one non-deleted ACTIVE curriculum version per Program in the initial design.
- Archiving a version must not physically delete its documents.
- Actual Student curriculum assignment is outside the initial scope.

Example:

```text
Program:
Bachelor of Computer Science

Version Code:
CS-2024

Version Name:
Computer Science Curriculum 2024

Academic Year:
2024–2025

Status:
ACTIVE
```

Migration SQL:

```sql
CREATE TABLE curriculum_versions (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    program_id BIGINT NOT NULL,
    version_code VARCHAR(50) NOT NULL,
    version_name VARCHAR(200) NOT NULL,
    academic_year_label VARCHAR(20) NOT NULL,
    description TEXT,
    effective_from DATE,
    effective_to DATE,
    status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE,
    created_by BIGINT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_by BIGINT,
    updated_at TIMESTAMP,

    CONSTRAINT fk_curriculum_versions_program
        FOREIGN KEY (program_id) REFERENCES programs(id),

    CONSTRAINT fk_curriculum_versions_created_by
        FOREIGN KEY (created_by) REFERENCES app_users(id),

    CONSTRAINT fk_curriculum_versions_updated_by
        FOREIGN KEY (updated_by) REFERENCES app_users(id),

    CONSTRAINT uk_curriculum_versions_program_code
        UNIQUE (program_id, version_code),

    CONSTRAINT chk_curriculum_versions_status
        CHECK (status IN ('ACTIVE', 'ARCHIVED')),

    CONSTRAINT chk_curriculum_versions_dates
        CHECK (
            effective_to IS NULL
            OR effective_from IS NULL
            OR effective_to >= effective_from
        )
);

CREATE UNIQUE INDEX uk_curriculum_versions_one_active
ON curriculum_versions(program_id)
WHERE status = 'ACTIVE' AND is_deleted = FALSE;

CREATE INDEX idx_curriculum_versions_program
ON curriculum_versions(program_id);
```

The one-active-version rule is a deliberate initial business decision. If official curricula legitimately overlap for different student cohorts, revise this policy before production migration.

## 5. Table 2 — document_categories

Keep category insertion separate from schema creation. Official categories may be inserted through controlled Admin APIs or an explicitly approved reference-data migration; never insert fake documents.

## 6. Table 3 — academic_documents

Purpose: store the logical document record independently from its file contents and processing state.

| Column                  | Type         | Constraint    |
| ----------------------- | ------------ | ------------- |
| `id`                    | BIGINT       | Identity PK   |
| `title`                 | VARCHAR(255) | NOT NULL      |
| `description`           | TEXT         | NULL          |
| `category_id`           | BIGINT       | NOT NULL FK   |
| `academic_year_label`   | VARCHAR(20)  | NOT NULL      |
| `curriculum_version_id` | BIGINT       | NULL FK       |
| `program_id`            | BIGINT       | NULL FK       |
| `department_id`         | BIGINT       | NULL FK       |
| `is_active`             | BOOLEAN      | DEFAULT TRUE  |
| `is_deleted`            | BOOLEAN      | DEFAULT FALSE |
| `created_by`            | BIGINT       | Nullable FK   |
| `created_at`            | TIMESTAMP    | NOT NULL      |
| `updated_by`            | BIGINT       | Nullable FK   |
| `updated_at`            | TIMESTAMP    | NULL          |

Scope rules:

- If `curriculum_version_id` is set, derive the Program and Department through that version's Program.
- Otherwise, `program_id` may identify a Program directly.
- Otherwise, `department_id` may identify a Department.
- If all three are NULL, the document is university-wide.
- Do not duplicate Program and Department identifiers when they can be derived from a more specific reference.
- Service logic must validate referenced scope relationships and prevent inconsistent combinations.

The UI must display the resolved Program and Department, even if they are not directly stored on the document row.

Migration SQL:

```sql
CREATE TABLE academic_documents (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    description TEXT,
    category_id BIGINT NOT NULL,
    academic_year_label VARCHAR(20) NOT NULL,
    curriculum_version_id BIGINT,
    program_id BIGINT,
    department_id BIGINT,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE,
    created_by BIGINT REFERENCES app_users(id),
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_by BIGINT REFERENCES app_users(id),
    updated_at TIMESTAMP,

    CONSTRAINT fk_academic_documents_category
        FOREIGN KEY (category_id)
        REFERENCES document_categories(id),

    CONSTRAINT fk_academic_documents_curriculum
        FOREIGN KEY (curriculum_version_id)
        REFERENCES curriculum_versions(id),

    CONSTRAINT fk_academic_documents_program
        FOREIGN KEY (program_id)
        REFERENCES programs(id),

    CONSTRAINT fk_academic_documents_department
        FOREIGN KEY (department_id)
        REFERENCES departments(id),

    CONSTRAINT chk_academic_documents_scope
        CHECK (
            (
                CASE WHEN curriculum_version_id IS NOT NULL THEN 1 ELSE 0 END
              + CASE WHEN program_id IS NOT NULL THEN 1 ELSE 0 END
              + CASE WHEN department_id IS NOT NULL THEN 1 ELSE 0 END
            ) <= 1
        )
);

CREATE INDEX idx_academic_documents_category
ON academic_documents(category_id);

CREATE INDEX idx_academic_documents_curriculum
ON academic_documents(curriculum_version_id);

CREATE INDEX idx_academic_documents_program
ON academic_documents(program_id);

CREATE INDEX idx_academic_documents_department
ON academic_documents(department_id);

CREATE INDEX idx_academic_documents_year
ON academic_documents(academic_year_label);

CREATE INDEX idx_academic_documents_active
ON academic_documents(is_active, is_deleted);
```

No unique constraint on document title alone. Different curriculum versions and academic years can use the same document title.

## 7. Table 4 — academic_document_files

Purpose: separate the logical document from uploaded physical file revisions.

This allows a document to retain its identity while its attached file is replaced later.

| Column              | Type         | Constraint                 |
| ------------------- | ------------ | -------------------------- |
| `id`                | BIGINT       | Identity PK                |
| `document_id`       | BIGINT       | NOT NULL FK                |
| `revision_number`   | INTEGER      | NOT NULL                   |
| `original_filename` | VARCHAR(255) | NOT NULL                   |
| `storage_key`       | VARCHAR(600) | NOT NULL, UNIQUE           |
| `mime_type`         | VARCHAR(150) | NOT NULL                   |
| `file_extension`    | VARCHAR(12)  | NOT NULL                   |
| `size_bytes`        | BIGINT       | NOT NULL                   |
| `sha256_checksum`   | CHAR(64)     | NOT NULL                   |
| `is_current`        | BOOLEAN      | DEFAULT TRUE               |
| `uploaded_by`       | BIGINT       | NOT NULL FK `app_users.id` |
| `uploaded_at`       | TIMESTAMP    | NOT NULL                   |

Rules:

- The real file is stored in protected application-controlled file/object storage.
- PostgreSQL stores file metadata, not raw file bytes.
- `storage_key` is generated by the backend; never trust a user-supplied path.
- A document may have multiple revisions.
- Each document may have at most one current revision.
- Replacing a file does not overwrite the previous revision's metadata.
- The file's SHA-256 checksum helps verify integrity; it is not a malware-scanning substitute.

Migration SQL:

```sql
CREATE TABLE academic_document_files (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    document_id BIGINT NOT NULL,
    revision_number INTEGER NOT NULL,
    original_filename VARCHAR(255) NOT NULL,
    storage_key VARCHAR(600) NOT NULL UNIQUE,
    mime_type VARCHAR(150) NOT NULL,
    file_extension VARCHAR(12) NOT NULL,
    size_bytes BIGINT NOT NULL,
    sha256_checksum CHAR(64) NOT NULL,
    is_current BOOLEAN NOT NULL DEFAULT TRUE,
    uploaded_by BIGINT NOT NULL,
    uploaded_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_academic_document_files_document
        FOREIGN KEY (document_id)
        REFERENCES academic_documents(id),

    CONSTRAINT fk_academic_document_files_uploaded_by
        FOREIGN KEY (uploaded_by)
        REFERENCES app_users(id),

    CONSTRAINT uk_academic_document_files_revision
        UNIQUE (document_id, revision_number),

    CONSTRAINT chk_academic_document_files_revision
        CHECK (revision_number > 0),

    CONSTRAINT chk_academic_document_files_size
        CHECK (size_bytes > 0)
);

CREATE UNIQUE INDEX uk_academic_document_files_one_current
ON academic_document_files(document_id)
WHERE is_current = TRUE;

CREATE INDEX idx_academic_document_files_document
ON academic_document_files(document_id);
```

## 8. Table 5 — academic_document_processing

Purpose: track ingestion/processing progress for each file revision.

| Column               | Type         | Constraint          |
| -------------------- | ------------ | ------------------- |
| `id`                 | BIGINT       | Identity PK         |
| `file_id`            | BIGINT       | NOT NULL, UNIQUE FK |
| `status`             | VARCHAR(30)  | NOT NULL            |
| `attempt_count`      | INTEGER      | DEFAULT 0           |
| `started_at`         | TIMESTAMP    | NULL                |
| `completed_at`       | TIMESTAMP    | NULL                |
| `last_error_code`    | VARCHAR(100) | NULL                |
| `last_error_message` | VARCHAR(500) | NULL                |
| `updated_at`         | TIMESTAMP    | NOT NULL            |

Supported statuses:

```text
UPLOADED
QUEUED
PROCESSING
CHUNKING
EMBEDDING
READY
FAILED
```

Meaning:

```text
UPLOADED
→ File securely stored and metadata committed.

QUEUED
→ Awaiting ingestion worker.

PROCESSING
→ File parsing/text extraction in progress.

CHUNKING
→ Extracted text is being split into chunks.

EMBEDDING
→ Vector embeddings are being generated/stored.

READY
→ All required indexing stages succeeded.

FAILED
→ Processing attempt failed.
```

Do not mark a file `READY` merely because uploading succeeded.

Migration SQL:

```sql
CREATE TABLE academic_document_processing (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    file_id BIGINT NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL DEFAULT 'UPLOADED',
    attempt_count INTEGER NOT NULL DEFAULT 0,
    started_at TIMESTAMP,
    completed_at TIMESTAMP,
    last_error_code VARCHAR(100),
    last_error_message VARCHAR(500),
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_academic_document_processing_file
        FOREIGN KEY (file_id)
        REFERENCES academic_document_files(id),

    CONSTRAINT chk_academic_document_processing_status
        CHECK (
            status IN (
                'UPLOADED',
                'QUEUED',
                'PROCESSING',
                'CHUNKING',
                'EMBEDDING',
                'READY',
                'FAILED'
            )
        ),

    CONSTRAINT chk_academic_document_processing_attempts
        CHECK (attempt_count >= 0)
);

CREATE INDEX idx_academic_document_processing_status
ON academic_document_processing(status);
```

## 9. Processing State Transitions

Allowed basic workflow:

```text
UPLOADED
    ↓
QUEUED
    ↓
PROCESSING
    ↓
CHUNKING
    ↓
EMBEDDING
    ↓
READY
```

Failure may occur at any processing stage:

```text
PROCESSING / CHUNKING / EMBEDDING
    ↓
FAILED
```

Retry:

```text
FAILED
    ↓
QUEUED
```

Transitions must be validated in the backend service, not by allowing Admin clients to set arbitrary status values.

For Step 13, the initial implementation may legitimately stop at `UPLOADED` or `QUEUED`, until the actual ingestion pipeline is implemented.

## 10. Document Archiving

`academic_documents.is_active` controls whether a document is eligible for normal use.

```text
is_active = TRUE
→ Active document

is_active = FALSE
→ Archived document
```

`is_deleted` is a separate soft-delete flag.

Archiving must not delete file revisions or metadata.

A document should be eligible for future AI retrieval only when:

```text
document.is_active = TRUE
document.is_deleted = FALSE
file.is_current = TRUE
processing.status = READY
```

Also apply the appropriate curriculum-version and access-scope rules.

## 11. AI Knowledge Base Statistics

The Figma screen shows:

```text
Total Documents
Ready
Processing
Failed
```

Do not store those counts in a separate statistics table.

Derive them from `academic_documents`, current `academic_document_files`, and `academic_document_processing`.

Suggested grouping:

```text
READY:
READY

PROCESSING:
UPLOADED, QUEUED, PROCESSING, CHUNKING, EMBEDDING

FAILED:
FAILED
```

Apply the same document activity/deletion filter consistently across all four counts.
