# 6. Final Enrollment Columns

| Column | Type | Constraint | Description |
|---|---|---|---|
| `id` | BIGINT | PK, Identity | Internal Enrollment ID |
| `student_id` | BIGINT | NOT NULL, FK → `students.id` | Student being enrolled |
| `course_section_id` | BIGINT | NOT NULL, FK → `course_sections.id` | Selected Course Section |
| `enrollment_date` | DATE | NOT NULL DEFAULT CURRENT_DATE | Enrollment date |
| `status` | VARCHAR(30) | NOT NULL | Enrollment status |
| `is_deleted` | BOOLEAN | NOT NULL DEFAULT FALSE | Soft-delete flag |
| `created_by` | BIGINT | NOT NULL, FK → `app_users.id` | Admin who created enrollment |
| `created_at` | TIMESTAMP | NOT NULL DEFAULT CURRENT_TIMESTAMP | Creation timestamp |
| `updated_by` | BIGINT | NULL, FK → `app_users.id` | Last Admin updater |
| `updated_at` | TIMESTAMP | NULL | Last update timestamp |

# 31. Duplicate Enrollment Constraint

A Student should not have two Enrollment rows for the exact same Course Section.

Add:

```sql
CONSTRAINT uk_enrollments_student_course_section
    UNIQUE (
        student_id,
        course_section_id
    )
```

This prevents:

```text
Student 15
Section 10

Enrollment A
+
Enrollment B
```

for the same Student/Section.

---

# 32. Re-enrollment Behavior

Because:

```text
student_id + course_section_id
```

is unique, if Enrollment previously became:

```text
WITHDRAWN
```

or:

```text
DROPPED
```

and the Student is later allowed to rejoin the exact same section, do NOT insert another duplicate Enrollment row.

Instead, future service logic may reactivate/update the existing Enrollment according to university policy.

This preserves one Enrollment lifecycle per:

```text
Student
+
Course Section
```

# 33. Prevent Student from Joining Two Sections of Same Course

Example invalid:

```text
Student:
STD-2024-0001

Course:
CS301

Semester:
Semester 1

Section 1:
SEC-01

Section 2:
SEC-02
```

The Student normally should not be ACTIVE/PENDING in both sections of the same Course in the same Semester.

Do NOT add:

```text

semester_id
```

to Enrollment merely to create a database UNIQUE constraint.

Instead validate at Service layer using joins.

# 34. Same-Course/Same-Semester Validation

Future Create service should check:

```text
Student
+
Course
+
Semester
+
status IN (PENDING, ACTIVE)
```

before creating Enrollment.

Conceptual query:

```sql
SELECT COUNT(*)
FROM enrollments e
JOIN course_sections cs
    ON cs.id = e.course_section_id
WHERE e.student_id = :studentId
  AND cs.course_id = :courseId
  AND cs.semester_id = :semesterId
  AND e.status IN ('PENDING', 'ACTIVE')
  AND e.is_deleted = FALSE;
```

If count > 0:

```text
Reject Enrollment
```

Recommended error:

```text
STUDENT_ALREADY_ENROLLED_IN_COURSE
```

# 44. Required Flyway SQL

Create:

```text
V{next}__create_enrollments.sql
```

Do NOT assume the version number.

The agent MUST inspect:

```text
src/main/resources/db/migration/
```

first.

Required SQL:

```sql
CREATE TABLE enrollments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    student_id BIGINT NOT NULL,

    course_section_id BIGINT NOT NULL,

    enrollment_date DATE NOT NULL DEFAULT CURRENT_DATE,

    status VARCHAR(30) NOT NULL,

    is_deleted BOOLEAN NOT NULL DEFAULT FALSE,

    created_by BIGINT NOT NULL,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    updated_by BIGINT,

    updated_at TIMESTAMP,

    CONSTRAINT uk_enrollments_student_course_section
        UNIQUE (
            student_id,
            course_section_id
        ),

    CONSTRAINT chk_enrollments_status
        CHECK (
            status IN (
                'PENDING',
                'ACTIVE',
                'WITHDRAWN',
                'DROPPED'
            )
        ),

    CONSTRAINT fk_enrollments_student
        FOREIGN KEY (student_id)
        REFERENCES students(id),

    CONSTRAINT fk_enrollments_course_section
        FOREIGN KEY (course_section_id)
        REFERENCES course_sections(id),

    CONSTRAINT fk_enrollments_created_by
        FOREIGN KEY (created_by)

    CONSTRAINT fk_enrollments_updated_by
        FOREIGN KEY (updated_by)
```

# 53. Recommended Create Validation

Future Enrollment Create service must validate in this order:

```text
1. Validate Student

2. Require Student not deleted

3. Require Student ACTIVE

4. Load Course Section

5. Require Section not deleted

6. Require Section status ACTIVE

7. Load Course

8. Load Semester through Section

9. Check exact Student + Section duplicate

10. Check Student not already in another Section
    of same Course + Semester

11. Validate capacity

12. Validate prerequisite rules when supported

13. Validate status

14. Persist Enrollment
```

# 65. Academic Year Filter

The current screenshot shows:

```text
Academic Year
```

but current normalized schema has no Enrollment Academic Year.

Do NOT fake this filter using:

```text
students.academic_year
```

because:

```text
students.academic_year
```

means the Student's current academic year and is not necessarily the academic year of a particular Enrollment.

If historical Enrollment Academic Year filtering is required, implement a proper:

```text
academic_years
```

or:

```text
academic_terms
```

model first.

Until then:

```text
remove/disable the Academic Year filter
```

or treat it as a future UI feature.

# 66. Important Academic Year Distinction

Do NOT confuse:

```text
students.academic_year
```

with:

```text
Enrollment Academic Year
```

Example:

```text
Student current academic year:
2026

Historical Enrollment:
2024
```

Using:

```text
students.academic_year
```

for historical Enrollment would produce incorrect records.

Therefore Enrollment should NOT reference the Student's `academic_year` for semester history.
