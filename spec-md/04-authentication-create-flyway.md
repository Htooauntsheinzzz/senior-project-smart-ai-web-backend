# 04 — Authentication Flyway Migration Specification

## 1. Project and scope

**Project:** Smart University Student Assistant App  
**Feature:** Authentication  
**Implementation step:** PostgreSQL schema creation through Flyway migrations only.

This document specifies four authentication tables, their constraints and relationships, supporting indexes, and a separate role seed migration. Store this specification as `spec-md/04-authentication-flyway-migration.md` in the backend repository.

The implementation deliverable is five versioned SQL migration files. This document includes their complete SQL; creating this specification does not itself apply migrations to a database.

Do not implement JWT, Redis, controllers, services, repositories, entities, DTOs, mappers, Spring Security flows, login/logout endpoints, refresh-token endpoints, or authentication business logic. Do not create Department tables or seed user accounts or passwords.

## 2. Preparation and migration rules

Before implementing the SQL migrations:

1. Read the applicable `AGENTS.md` instructions.
2. Inspect all specifications in `spec-md/`, including `02-project-structure.md` and the existing database/infrastructure setup specification.
3. Inspect existing migrations and the configured Flyway schema and migration locations.
4. Inspect Flyway history in the target development/test database and determine the next unused migration versions across all features.
5. Confirm that these tables do not already exist. If they do, reconcile the existing schema and specifications before creating a conflicting initial migration.
6. Reuse the project's PostgreSQL and Flyway setup. Flyway owns schema changes; Hibernate must not generate or update this schema.

Place every SQL file in:

```text
src/main/resources/db/migration/
```

Use unique, increasing versions following the repository's established numbering convention. Never overwrite, rename, or change the checksum of a migration already applied to a shared environment. Fix applied schema changes with a new migration. Do not use `IF NOT EXISTS` or seed conflict suppression to conceal an unexpected existing schema.

The SQL below uses unqualified table names. Run all five migrations in the same configured application schema. Validation examples use `public`; substitute the configured schema when different.

If the project has no existing migrations, use these exact filenames:

| Order | Filename | Contents |

| 3 | `V3__create_app_user_roles.sql` | Role assignments, foreign keys, unique user/role pair, supporting indexes |

## 4. Shared schema conventions

- All primary keys are `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Omit IDs when inserting normal records and role seeds.
- `TIMESTAMP` means PostgreSQL `TIMESTAMP WITHOUT TIME ZONE`, retaining the existing authentication specification. Use a consistent UTC database/session convention; these columns do not retain time-zone offsets.
- `created_at` defaults to `CURRENT_TIMESTAMP`. Nullable timestamps have no default unless explicitly shown.
- `updated_at` is not automatically updated. No update triggers are part of this migration task.
- Every listed foreign key uses PostgreSQL's default `ON DELETE NO ACTION` and `ON UPDATE NO ACTION`, with immediate, non-deferrable checking. Do not introduce cascading deletes.
- Nullable audit references permit initial account provisioning without an existing creator. Non-null references must identify existing users.
- Soft deletion does not remove rows, free unique email/employee identifiers, delete credentials, or remove role assignments.
- Text uniqueness follows the configured PostgreSQL collation and the ordinary unique constraints below. No case-insensitive email normalization, functional unique index, or `citext` extension is introduced.

## 5. Table: `app_roles`

Stores the application's administrative authorization roles.

| Attribute | PostgreSQL type | Nullability / default | Constraints and meaning |
| --- | --- | --- | --- |
| `id` | `BIGINT` | NOT NULL; generated identity | Primary key |
| `role_code` | `VARCHAR(50)` | NOT NULL; no default | Unique machine-readable code |
| `role_name` | `VARCHAR(100)` | NOT NULL; no default | Unique display name |
| `description` | `VARCHAR(500)` | NULL; no default | Role description |
| `is_active` | `BOOLEAN` | NOT NULL; `TRUE` | Whether the role is active |
| `created_at` | `TIMESTAMP` | NOT NULL; `CURRENT_TIMESTAMP` | Creation time |
| `updated_at` | `TIMESTAMP` | NULL; no default | Most recent update time |

### SQL — `V1__create_app_roles.sql`

```sql
CREATE TABLE app_roles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    role_code VARCHAR(50) NOT NULL,
    role_name VARCHAR(100) NOT NULL,
    description VARCHAR(500),
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP,

    CONSTRAINT uk_app_roles_role_code UNIQUE (role_code),
    CONSTRAINT uk_app_roles_role_name UNIQUE (role_name)
);
```

## 6. Table: `app_users`

Stores administrative user profiles and account information. Credentials are stored separately.

| Attribute | PostgreSQL type | Nullability / default | Constraints and meaning |
| --- | --- | --- | --- |
| `id` | `BIGINT` | NOT NULL; generated identity | Primary key |
| `employee_id` | `VARCHAR(50)` | NOT NULL; no default | Unique university employee ID, such as `RSU-001` |
| `first_name` | `VARCHAR(100)` | NOT NULL; no default | First name |
| `last_name` | `VARCHAR(100)` | NOT NULL; no default | Last name |
| `email` | `VARCHAR(255)` | NOT NULL; no default | Unique email/login identifier |
| `phone_number` | `VARCHAR(30)` | NULL; no default | Optional phone number |
| `department_id` | `BIGINT` | NULL; no default | Future department reference; **no foreign key** |
| `account_status` | `VARCHAR(30)` | NOT NULL; no default | Account status supplied explicitly on insertion |
| `is_deleted` | `BOOLEAN` | NOT NULL; `FALSE` | Soft-delete flag |
| `created_by` | `BIGINT` | NULL; no default | FK to `app_users.id`; account creator |
| `created_at` | `TIMESTAMP` | NOT NULL; `CURRENT_TIMESTAMP` | Creation time |
| `updated_by` | `BIGINT` | NULL; no default | FK to `app_users.id`; most recent updater |
| `updated_at` | `TIMESTAMP` | NULL; no default | Most recent update time |

Expected account status values are `ACTIVE`, `INACTIVE`, `LOCKED`, and `SUSPENDED`. Retain the referenced schema's `VARCHAR(30)` representation: this migration does not add a status enum, status lookup table, or status-value check constraint. Consequently, the database enforces non-nullness and length, but not membership in this expected set. Database enforcement of that set would require an explicitly agreed schema change.

### Department rule

`department_id` must remain `BIGINT NULL` with **no foreign key**, because Department Management does not exist yet. Both null and non-null values are allowed without department existence checks. An index on this column does not create a relationship. A future Department migration must reconcile any non-null orphan values before adding its foreign key.

### SQL — `V2__create_app_users.sql`

```sql
CREATE TABLE app_users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    employee_id VARCHAR(50) NOT NULL,
    first_name VARCHAR(100) NOT NULL,
    last_name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL,
    phone_number VARCHAR(30),
    department_id BIGINT,
    account_status VARCHAR(30) NOT NULL,
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE,
    created_by BIGINT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_by BIGINT,
    updated_at TIMESTAMP,

    CONSTRAINT uk_app_users_employee_id UNIQUE (employee_id),
    CONSTRAINT uk_app_users_email UNIQUE (email),
    CONSTRAINT fk_app_users_created_by
        FOREIGN KEY (created_by) REFERENCES app_users(id),
    CONSTRAINT fk_app_users_updated_by
        FOREIGN KEY (updated_by) REFERENCES app_users(id)
);

CREATE INDEX idx_app_users_department_id ON app_users (department_id);
CREATE INDEX idx_app_users_created_by ON app_users (created_by);
CREATE INDEX idx_app_users_updated_by ON app_users (updated_by);
```

## 7. Table: `app_user_roles`

Maps users to roles, allowing multiple roles per user and multiple users per role. Each user/role pair may occur only once.

| Attribute | PostgreSQL type | Nullability / default | Constraints and meaning |
| --- | --- | --- | --- |
| `id` | `BIGINT` | NOT NULL; generated identity | Primary key |
| `user_id` | `BIGINT` | NOT NULL; no default | FK to `app_users.id`; assigned user |
| `role_id` | `BIGINT` | NOT NULL; no default | FK to `app_roles.id`; assigned role |
| `assigned_at` | `TIMESTAMP` | NOT NULL; `CURRENT_TIMESTAMP` | Assignment time |
| `assigned_by` | `BIGINT` | NULL; no default | FK to `app_users.id`; assigning user |

The composite unique constraint is `uk_app_user_roles_user_role (user_id, role_id)`.

### SQL — `V3__create_app_user_roles.sql`

```sql
CREATE TABLE app_user_roles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    assigned_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    assigned_by BIGINT,

    CONSTRAINT fk_app_user_roles_user
        FOREIGN KEY (user_id) REFERENCES app_users(id),
    CONSTRAINT fk_app_user_roles_role
        FOREIGN KEY (role_id) REFERENCES app_roles(id),
    CONSTRAINT fk_app_user_roles_assigned_by
        FOREIGN KEY (assigned_by) REFERENCES app_users(id),
    CONSTRAINT uk_app_user_roles_user_role UNIQUE (user_id, role_id)
);

CREATE INDEX idx_app_user_roles_role_id ON app_user_roles (role_id);
CREATE INDEX idx_app_user_roles_assigned_by ON app_user_roles (assigned_by);
```

## 8. Table: `appuser_credentials`

Use the exact name `appuser_credentials`, not `app_user_credentials`. Stores credential metadata separately from profile data.

| Attribute | PostgreSQL type | Nullability / default | Constraints and meaning |
| --- | --- | --- | --- |
| `id` | `BIGINT` | NOT NULL; generated identity | Primary key |
| `user_id` | `BIGINT` | NOT NULL; no default | Unique; FK to `app_users.id` |
| `password_hash` | `VARCHAR(255)` | NOT NULL; no default | BCrypt password hash supplied by a later feature |
| `force_password_change` | `BOOLEAN` | NOT NULL; `TRUE` | Whether a password change is required |
| `password_changed_at` | `TIMESTAMP` | NULL; no default | Most recent password change |
| `failed_login_attempts` | `INTEGER` | NOT NULL; `0` | Failed login counter |
| `locked_until` | `TIMESTAMP` | NULL; no default | Temporary lock expiration |
| `created_at` | `TIMESTAMP` | NOT NULL; `CURRENT_TIMESTAMP` | Creation time |
| `updated_at` | `TIMESTAMP` | NULL; no default | Most recent update time |

Each credential row belongs to exactly one existing user. The unique `user_id` permits at most one credential row per user; it does not require every user to already have credentials. The database does not validate BCrypt format or implement password checking. The referenced schema does not include a non-negative check on the failed-login counter; maintaining its intended non-negative meaning belongs to later logic unless a separate schema change adds that constraint.

Do not add plaintext password, temporary password, confirmation password, access token, refresh token, or refresh-token hash columns. Do not insert passwords or password hashes in these migrations.

### SQL — `V4__create_appuser_credentials.sql`

```sql
CREATE TABLE appuser_credentials (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    force_password_change BOOLEAN NOT NULL DEFAULT TRUE,
    password_changed_at TIMESTAMP,
    failed_login_attempts INTEGER NOT NULL DEFAULT 0,
    locked_until TIMESTAMP,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP,

    CONSTRAINT uk_appuser_credentials_user UNIQUE (user_id),
    CONSTRAINT fk_appuser_credentials_user
        FOREIGN KEY (user_id) REFERENCES app_users(id)
);
```

## 9. Relationships

| Referencing column | Referenced column | Relationship |
| --- | --- | --- |
| `app_users.created_by` | `app_users.id` | Optional creator; one creator may create many accounts |
| `app_users.updated_by` | `app_users.id` | Optional updater; one updater may update many accounts |
| `app_user_roles.user_id` | `app_users.id` | Each assignment has one user; a user has zero or more assignments |
| `app_user_roles.role_id` | `app_roles.id` | Each assignment has one role; a role has zero or more assignments |
| `app_user_roles.assigned_by` | `app_users.id` | Optional assigning user; a user may make many assignments |
| `appuser_credentials.user_id` | `app_users.id` | A user has zero or one credential row |
| `app_users.department_id` | None | Nullable placeholder, not a foreign key |

There are exactly six foreign keys. Physical deletion of a referenced user or role is blocked while dependent references remain. This specification adds no automatic cleanup behavior.

## 10. Role seed migration

Seed exactly these roles, obtaining their IDs from the identity column:

| Role code | Role name | Active | Description |
| --- | --- | --- | --- |

| `ADMIN` | Admin | `TRUE` | General administrative access. |
| `ACADEMIC_ADMIN` | Academic Admin | `TRUE` | Administrative access to academic management features. |

Descriptions document intended roles; this migration does not implement permissions or authorization.

## 11. Index guidance

PostgreSQL creates indexes for primary keys and unique constraints. The SQL therefore already supplies:

| Table | Automatically indexed keys |
| --- | --- |
| `app_roles` | `id`, `role_code`, `role_name` |
| `app_users` | `id`, `employee_id`, `email` |
| `app_user_roles` | `id`, `(user_id, role_id)` |
| `appuser_credentials` | `id`, `user_id` |

Do not create duplicate indexes for these keys. The leading `user_id` in `(user_id, role_id)` also supports lookup by user; omit a separate `app_user_roles(user_id)` index. The unique credential-owner index already supports lookup by user.

The five explicit indexes included in the table migrations cover `app_users.department_id`, `app_users.created_by`, `app_users.updated_by`, `app_user_roles.role_id`, and `app_user_roles.assigned_by`. Foreign keys do not automatically create indexes on referencing columns; the audit and role indexes support those references and related lookups.

Do not add standalone indexes on `account_status`, `is_deleted`, or `is_active` by default. Their usefulness depends on data distribution and actual query patterns. Consider composite or partial indexes in a later migration only after representative query-plan measurements. Keep the specified indexes in their owning table migration; no sixth migration is required.

## 12. Validation procedure

These are required checks for the later migration implementation. They are not a claim that migrations have already run while preparing this Markdown specification.

### 12.1 Static review

1. Confirm filenames, unique versions, dependency order, and the migration directory.
2. Compare each SQL column against its attribute table, including lengths, nullability, identity declarations, defaults, and constraint names.
3. Confirm four primary keys, six unique constraints, and six foreign keys.
4. Confirm `department_id` is nullable and has no foreign key.
5. Confirm no secrets, seeded users, token columns, application code, duplicate indexes, or unrelated schema changes were added.

### 12.2 Flyway execution

Use the project's already configured Flyway runner against an isolated development/test PostgreSQL database. Supply connection settings through the existing configuration without putting credentials in SQL files. If a configured Flyway CLI is available, the lifecycle is:

```sh
flyway info
flyway migrate
flyway validate
flyway info
```

When the project runs Flyway through Spring Boot or another established runner, perform the equivalent operations through that runner; do not assume the Maven Flyway plugin or standalone CLI is installed.

- First apply existing project migrations and these five migrations to a fresh test database.
- If the project already has a schema, also test upgrading an isolated database at the immediately preceding migration version.
- Confirm all five migrations succeed and have the expected checksums/history entries.
- Run migration again through Flyway; expect no pending migrations, no duplicate seed rows, and successful validation.
- Do not run Flyway `clean`, reset shared data, alter history, or use `repair` to conceal validation failures.

### 12.3 Schema inspection

Run against the configured schema; examples assume `public` and Flyway's default history table name.

```sql
SELECT table_name, column_name, data_type,
       character_maximum_length, is_nullable,
       column_default, is_identity, identity_generation
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN (
      'app_roles', 'app_users', 'app_user_roles', 'appuser_credentials'
  )
ORDER BY table_name, ordinal_position;

SELECT c.conrelid::regclass AS table_name,
       c.conname AS constraint_name,
       c.contype AS constraint_type,
       pg_get_constraintdef(c.oid) AS definition
FROM pg_constraint c
JOIN pg_class t ON t.oid = c.conrelid
JOIN pg_namespace n ON n.oid = t.relnamespace
WHERE n.nspname = 'public'
  AND t.relname IN (
      'app_roles', 'app_users', 'app_user_roles', 'appuser_credentials'
  )
ORDER BY table_name, constraint_name;

SELECT tablename, indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public'
  AND tablename IN (
      'app_roles', 'app_users', 'app_user_roles', 'appuser_credentials'
  )
ORDER BY tablename, indexname;

SELECT role_code, role_name, description, is_active
FROM public.app_roles
ORDER BY role_code;

SELECT installed_rank, version, description, script, checksum, success
FROM public.flyway_schema_history
ORDER BY installed_rank;
```

Expected baseline: four application tables, four identity primary keys, six unique constraints, six foreign keys, five explicitly created indexes, and exactly the three seeded roles. The default primary-key and unique indexes add ten indexes, for fifteen indexes across these four tables. The Flyway history table is additional infrastructure, not an authentication table.

### 12.4 Behavioral checks

Use temporary fixtures in the isolated test database. Keep checks outside production migration files. Use separate transactions or savepoints for expected failures, then roll back fixtures. Identity sequences may advance even when fixture transactions are rolled back.

| Check | Expected result |
| --- | --- |
| Insert a user with required profile fields and `account_status = 'ACTIVE'`, omitting optional fields | Success; generated ID, `is_deleted = FALSE`, populated `created_at` |
| Insert with `department_id = NULL` | Success |
| Set `department_id` to a non-null test value without a Department table | Success; no department FK exists |
| Repeat an existing employee ID or email | Unique constraint violation |
| Repeat a role code or role name | Unique constraint violation |
| Omit or explicitly null a required non-defaulted column | NOT NULL violation |
| Supply a non-existent `created_by`, `updated_by`, or `assigned_by` user ID | Foreign key violation |
| Assign an existing role to an existing user | Success; populated `assigned_at` |
| Repeat that user/role pair | Unique constraint violation |
| Assign a different existing role to the same user | Success |
| Assign a non-existent user or role | Foreign key violation |
| Insert credentials for an existing user using a disposable test BCrypt hash | Success; force-change `TRUE`, failed attempts `0`, optional timestamps null |
| Insert a second credential row for the same user | Unique constraint violation |
| Insert credentials for a non-existent user | Foreign key violation |
| Physically delete a user or role still referenced by another row | Foreign key violation |
| Soft-delete a user with dependent rows | Success; dependent rows remain and unique identifiers remain reserved |
| Re-run Flyway migration | No migrations reapplied; three seed rows remain |

Select IDs of non-existent records deliberately rather than assuming a particular unused identity number. Never add fixture users, fixture hashes, or validation statements to the five migration files.
